## 🔐 需求一：權限架構分析

### 權限流程
```
請求 → AuthenticationInterceptor（session["userData"] 存在?）
      → PrivilegeInterceptor（session["menuList"] 包含 ActionName?）
      → XauthService.checkPriv()（部分 Action 額外呼叫）
```

### Session 內容
| Key | 值 | 來源 |
|-----|----|------|
| `userData` | XauthUsers 物件 | LoginAction 登入成功 |
| `compData` | XauthCompany 物件 | LoginAction 登入成功 |
| `menuList` | List\<String\>（Action 代碼清單） | MenuAction AJAX 呼叫後 |

### USER_TYPE 說明
| 值 | 說明 |
|----|------|
| `"0"` | 系統管理員（init.properties 超級帳號） |
| `"1"` | 總公司/管理人員 |
| `"2"` | 廠商用戶（受最嚴格限制） |

### ⚠️ 發現的安全缺口（PrivilegeInterceptor）

```java
// 當 menuList 為 null 時，直接放行所有 Action！
if (menuList != null && menuList.size() > 0) {
    // 只在有 menuList 時才做權限檢查
}
return actionInvocation.invoke();  // ← null 時直接通過
```

**修正方向**：menuList 為 null 時應拒絕存取（除白名單 Action）。

## 🔑 需求二：強制改密功能

### DB 現況
`PERMSMGR.XAUTH_USERS` 目前**缺少**以下欄位：
- `FORCE_CHG_PWD` CHAR(1) — 強制改密旗標
- `PWD_UPD_DATE` TIMESTAMP — 最後改密時間
- `LOGIN_STATUS` CHAR(1) — 登入狀態

### DB 異動 SQL（DB2 語法）
```sql
ALTER TABLE PERMSMGR.XAUTH_USERS
  ADD COLUMN FORCE_CHG_PWD CHAR(1) DEFAULT '0' NOT NULL,
  ADD COLUMN PWD_UPD_DATE   TIMESTAMP,
  ADD COLUMN LOGIN_STATUS   CHAR(1) DEFAULT '1' NOT NULL;
```

### 實作方案概要
1. `XauthUsers.java` — 新增欄位
2. `XauthUsersMapper.xml` — 新增 ResultMap 欄位、`updatePassword` SQL
3. `LoginAction.java` — 登入成功後判斷 `forceChgPwd`，寫入 `session["forceChangePwd"]="Y"`
4. `AuthenticationInterceptor.java` — 攔截非改密 Action，導向改密頁面
5. **新建** `ChangePasswordAction.java` + `changePassword.jsp`
6. Struts XML — 新增 `forceChangePwd` global-result 及 ChangePassword action

### 安全注意事項
- 改密成功後必須 `session.invalidate()` 重建 Session（防 Session 固定攻擊）
- 舊密碼驗證為後端強制執行
- 改密頁面不使用 mainLayout，避免側邊選單可點擊

## 📊 需求三：AM001 vs AM002 差異分析

### SQL 核心差異對照

| 比對項目 | AM001（`sel_mg001_01`） | AM002（`sel_rpt_001`） |
|---------|----------------------|----------------------|
| 資料表 | `PERMSMGR.APPLY_MAIN` | `APPLY_MAIN`（無 Schema） |
| **狀態過濾** | **無過濾（含作廢）** | **`NOW_STATUS != '999'`** |
| 日期粒度 | 精確到秒（begDateStr/endDateStr） | 年月（begYm/endYm，格式 YYYYMM） |
| 聚合 | 無，逐筆回傳 | GROUP BY 年月，COUNT+SUM |
| 子公司邏輯 | 無 | Sheet 2 LEFT JOIN 子公司 |

### 最可能的差異原因（優先順序）

1. **🔴 狀態過濾差異**：AM001 含 `NOW_STATUS='999'`（作廢）資料，AM002 排除 → AM001 件數 ≥ AM002 件數
2. **🟡 Schema 前綴差異**：DB2 current schema 設定可能導致查詢不同資料
3. **🟡 日期邊界差異**：AM001 可精確到日/秒，AM002 只能以月為單位
4. **🟢 REFUND_AMT vs BACK_AMT**：確認用戶認知的「退稅金額」對應哪個欄位

### 驗證 SQL（DB2）
```sql
-- 逐月比對含/不含作廢的差異
SELECT TO_CHAR(TRADE_DATE, 'YYYYMM') AS MONTH,
       COUNT(*) AS TOTAL_COUNT,
       COUNT(CASE WHEN NOW_STATUS != '999' THEN 1 END) AS VALID_COUNT,
       COUNT(CASE WHEN NOW_STATUS = '999' THEN 1 END) AS CANCEL_COUNT,
       SUM(CASE WHEN NOW_STATUS != '999' THEN UNV_AMT ELSE 0 END) AS VALID_UNV,
       SUM(CASE WHEN NOW_STATUS != '999' THEN BACK_AMT ELSE 0 END) AS VALID_BACK
FROM PERMSMGR.APPLY_MAIN
WHERE SELLER_ID = '目標統編'
  AND TO_CHAR(TRADE_DATE, 'YYYYMM') BETWEEN '202401' AND '202412'
GROUP BY TO_CHAR(TRADE_DATE, 'YYYYMM')
ORDER BY 1;
```

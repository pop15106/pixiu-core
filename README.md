# PixiuCore 母體

**把常用的 AI 工作規則放在一起，讓查資料、寫程式、做檢查與交接都有一致的做法。**

你可以把 PixiuCore 看成 AI 的工作手冊。不同工具共用同一份規則，再依本次需求讀取需要的內容。開始工作時只讀簡短入口，詳細規格留到用得上時再讀。

## 能幫你做什麼？

| 你想做的事 | 母體提供的幫助 |
| --- | --- |
| 把需求說清楚 | 整理目標、限制、待確認事項及完成條件 |
| 寫程式或修問題 | 理解現有程式，再修改、測試與說明影響 |
| 比較方案、查資料 | 找支持與反對的證據，說明取捨及資料缺口 |
| 檢查風險 | 記錄風險、負責人、處理方法與驗證結果 |
| 接續前次工作 | 保存決策、目前進度、未完成事項及下一步 |
| 換一個 AI 工具工作 | 沿用母體規則，並確認新工具實際支援哪些操作 |

## 怎麼開始？

### 在工作機上使用

先把這個專案下載到固定位置。已經有母體的人，先保留尚未完成的修改，再更新原本的專案。

在母體資料夾內，用 PowerShell 執行：

```powershell
.\setup_zh.bat
```

完成後另開一個終端視窗，讓設定生效。接著同步 Codex、Claude 與 Gemini 的簡短入口：

```powershell
powershell -ExecutionPolicy Bypass -File "scripts\entry-sync\Sync-PixiuGlobalEntries.ps1" -Action Apply -ConfirmApply
```

入口同步會先備份既有檔案。若要安裝 Claude Code 的其他整合、搬到新電腦或解除安裝，請看[安裝說明](scripts/setup/README.md)。Codex 的原生技能發布方式另見 [Codex 安裝與還原說明](scripts/codex-native-core/README.zh-TW.md)。

第三方資安技能庫、私人專案清單及個人記憶都是另外管理的內容，有需要再設定。完整操作保留在[技術導覽](docs/pixiu-core-reference-2026-08-09.md)。

### 在 ChatGPT 使用

母體已提供 [ChatGPT 轉換與安裝說明](scripts/chatgpt-core/README.zh-TW.md)。做法是建立 **一個 PixiuCore Skill**，把其他技能及工作流程當成參考規格，依需求載入。

整體分成三層：

| 位置 | 負責什麼 |
| --- | --- |
| GitHub 母體 | 保存完整工作規則、程式及版本，作為主要來源 |
| ChatGPT Skill | 保存已核對版本的完整規格，提供簡短入口與按需讀取工具 |
| 每次對話 | 用 `開 CR`、`Pro析`、`X析` 等說法選取流程，只讀本次需要的內容 |

既有 Workflow 會保留成 Skill 可讀取的流程步驟。需要工作機服務、排程或其他工具的步驟，仍要有實際連接的執行環境。

安裝需要通過 ChatGPT 的檢查。只有實際登錄成功，且回讀版本與檔案核對通過後，才算安裝完成。技能頁尚未更新時，可以重新整理頁面。

若安全掃描未通過，保留待安裝版本，依已確認的問題修正後再驗證。沒有具體原因時如實回報，不把檔案準備完成寫成安裝成功。

Skill 提供的是工作方法。讀取電腦檔案、修改程式、推送 GitHub 或長時間接續工作，還需要對應工具已連接並取得有效授權。

## 常用說法

在已載入母體的環境，可以直接這樣說：

| 說法 | 會做什麼 |
| --- | --- |
| `需求確認` | 整理需求、限制與完成條件 |
| `開 CR` | 啟動多輪分析、反證與檢查流程 |
| `CR 研究` | 研究問題，核對來源、主張與反對證據 |
| `CR 風險盤點` | 找出風險、影響範圍與待確認事項 |
| `CR 風險審查` | 檢查風險處理是否有足夠證據 |
| `CR 完整自動接力` | 接續研究、修改、驗證與交接；執行範圍以可用工具及授權為準 |
| `CRD` | 使用指定的純文字深入分析流程 |
| `Pro析`／`X析` | 使用對應的純文字分析規格 |
| `/go` | 進入變更覆核與收尾檢查 |

`CRD`、`Pro析`、`X析` 是自訂工作方式，名稱不代表已切換官方模型或付費方案。明確說「不要開 CR」時，保留原本任務，不自動啟動。

更多入口請看[技能索引](skills/INDEX.md)與[工作流程目錄](.agent/workflows/)。

## CR 是怎麼檢查問題的？

CR 是一套多輪檢查流程：先弄清楚要解決什麼，再提出判斷、找證據、找反例，必要時修改方案，最後確認是否符合完成條件。

這次補強了幾個重點：

1. **結論要對得上需求。** 每個主要判斷都要有依據，並區分已知事實、推論與尚未確認的假設。
2. **支持與反對的資料都要看。** 多個網站引用同一份資料時，會回到原始出處核對。
3. **方案要能比較。** 說清楚成本、好處、代價，以及什麼條件改變後需要重新判斷。
4. **風險處理要有證據。** 記錄負責人、處理方法、適用版本及環境。接受風險需要可回讀的使用者紀錄。
5. **舊結果需要確認是否仍適用。** 舊帳本中的「已通過」，不能直接當成新版本已完成。

程式檢查可以確認紀錄與證據是否符合規則；真實授權、來源可信度與產品實際表現，仍需依原始資料和實測判斷。

完整規範請看 [CR 說明](scripts/critical-relay/README.md)與[風險檢查規範](vault/governance/cr-risk-review.md)。

## 會不會把對話塞滿？

一次讀進所有規則、技能與歷史紀錄，會增加上下文負擔。目前採用以下方式控制：

- 開始時只讀簡短入口。
- 每次需求最多選取三類相關能力。
- 大型文件分段讀取，每次最多 80 行，整份回傳資料最多 12,000 位元組；特殊字元與附加欄位也計入，必要內容會接著讀完。
- 同一版本已讀過的規格，以章節與摘要接續使用。
- 證據原文留在檔案，對話保留目標、決策、未解風險與下一步。

12,000 位元組是這套讀取工具的單次輸出上限，與 ChatGPT 的上下文容量分開計算。

這些做法保留原有功能，並降低重複載入。長對話仍會累積內容，因此也需要適時整理摘要與交接紀錄。詳細做法見[母體載入政策](vault/context/ai-mothership-loading-policy.md)。

## 修改後怎麼確認？

核心檢查使用 Node.js 22。在母體資料夾執行：

```powershell
node scripts/critical-relay/test-runner.js
```

測試會保存結果與證據。工作機的安裝、還原與服務整合有各自的檢查，完整入口請看 [DevSpace 說明](scripts/devspace-portable/WORKFLOW.zh-TW.md)。

回報時會分開說明「程式測試通過」、「實際產品已驗證」與「外部服務已完成」，避免把其中一項當成全部完成。

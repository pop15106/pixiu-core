# 🧠 Prompt Engineering Skill — 自動精煉模組

> **隸屬層級**：L4（技能層）
> **觸發方式**：自動偵測，無需手動呼叫
> **審批規則**：精煉結果產出後，必須停下來等待用戶確認，才可執行後續任務

---

## 🎯 階段一：清晰度評分（觸發閘門）

收到用戶輸入後，**先評分，再決定是否精煉**。避免每次都跑精煉流程，節省 token。

### 評分維度（各 1–10 分）

| 維度 | 說明 | 低分特徵 |
|------|------|---------|
| **清晰度** | 目標是否明確無歧義 | 「幫我弄一下那個功能」 |
| **具體度** | 需求細節是否足夠 | 缺少技術棧、格式、範圍 |
| **脈絡** | 背景資訊是否充足 | 不知道為什麼要做這件事 |
| **完整度** | 必要元素是否齊全 | 缺角色、缺約束、缺預期輸出 |
| **結構** | 表達是否有條理 | 單句、口語、思緒散亂 |

### 觸發規則

```
總分 = (清晰度 + 具體度 + 脈絡 + 完整度 + 結構) / 5

總分 < 6.0   → 強制啟動精煉流程
總分 6.0-7.5 → 輕量精煉（僅補充缺失維度）
總分 > 7.5   → 直接執行，不精煉（零額外負擔）
```

> **例外**：用戶訊息以 `*`、`/`、`#` 開頭時，跳過評分直接執行。

## 🔀 階段二：框架選擇（自動判斷）

依任務類型自動選擇最合適的精煉框架：

```
這是內容創作或寫作任務？（部落格、文案、文件）
├─ 是 → CO-STAR（脈絡 / 目標 / 風格 / 語氣 / 受眾 / 格式）
└─ 否 ↓

這是多步驟流程或系統性程序？（Code Review、分析、規劃）
├─ 是 → RISEN（角色 / 指令 / 步驟 / 目標 / 約束）
└─ 否 ↓

這是資料處理或轉換任務？（解析、格式化、報表）
├─ 是 → RISE-IE（角色 / 輸入 / 步驟 / 預期輸出）
└─ 否 ↓

這是需要範例參考的任務？（仿寫、樣板生成）
├─ 是 → RISE-IX（角色 / 指令 / 步驟 / 範例）
└─ 否 ↓

這是高精度任務，需要明確的做／不做清單？（安全合規、標準化程式碼）
├─ 是 → TIDD-EC（任務 / 指令 / 要做 / 禁止 / 範例 / 脈絡）
└─ 否 ↓

這是推理或除錯任務？（根因分析、邏輯推導）
├─ 是 → Chain of Thought（逐步推理鏈）
└─ 否 ↓

這是 AI 協作流程設計？（Multi-Agent、自動化）
├─ 是 → RISEN + TIDD-EC 混合
└─ 否 → RTF（角色 / 任務 / 格式）— 簡單任務用
```

### 框架快速對照表

| 任務類型 | 推薦框架 | 原因 |
|---------|---------|------|
| 部落格、文案、說明文件 | CO-STAR | 受眾與語氣至關重要 |
| Code Review、流程規劃 | RISEN | 多步驟、有明確約束 |
| 資料解析、格式轉換 | RISE-IE | 輸入輸出明確 |
| 仿寫、樣板生成 | RISE-IX | 需要參考範例 |
| 安全性、合規性程式碼 | TIDD-EC | 需要明確的禁止清單 |
| Debug、根因分析 | Chain of Thought | 需要逐步推理 |
| AI 協作流程設計 | RISEN + TIDD-EC | 多角色、複雜約束 |
| 簡單明確的單一需求 | RTF | 輕量、快速 |

## 🔒 階段四：等待審批（強制閘門）

產出精煉結果後，**必須停下來**輸出以下詢問，不得自動執行：

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
請確認以下事項後再執行：

1. 這個 prompt 要套用到哪個範圍？
   □ 全專案（CLAUDE.md 已覆蓋，無需額外設定）
   □ 特定資料夾（建議加 instruction）
   □ 特定檔案（建議加 instruction）

2. 是否需要補充 instruction？
   □ 不需要，直接執行
   □ 需要，補充以下商業邏輯或約束：[請說明]

（回覆「執行」或「加上 [說明] 後執行」）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

獲得明確指示後，依用戶選擇進入對應路徑：
- 「直接執行」→ 進入執行階段
- 「加上 [說明] 後執行」→ 先產生 instruction 檔案，再執行

符合 Pixiu L0 憲法層「絕對用戶審批閘門」規定。

## 📋 階段五：Instruction 自動產生（選用）

若用戶選擇補充 instruction，AI 自動產生對應檔案後再執行主任務。

### 存放路徑

```
[用戶指定的資料夾]/.claude/instructions.md
```

### 產生格式

```markdown
---
applyTo: [用戶指定的路徑，例如 src/orders/**]
---

[從精煉後的 prompt 萃取出的商業邏輯與模組專屬約束]
```

### 萃取原則

- **只寫這個模組獨有的內容**：商業邏輯、技術約束、命名規範、資料格式
- **不重複全域規則**：語言設定、安全規範、審批流程已由 CLAUDE.md 覆蓋，不重複寫
- **具體勝於抽象**：「金額欄位一律用 decimal，禁止 float」優於「注意資料型別」

### 範例

用戶說：「針對 `src/orders/`，所有交易必須在 transaction 內，金額用 decimal」

自動產生：

```markdown
---
applyTo: src/orders/**
---

## 訂單模組專屬規範

- 所有資料庫操作必須包在 transaction 內，禁止裸寫
- 金額相關欄位一律使用 decimal，嚴禁 float 或 double
- 訂單狀態變更必須記錄 audit log，格式：[時間][操作者][舊狀態→新狀態]
```

產生完畢後，**再次停下來**確認用戶是否核可 instruction 內容，核可後才執行主任務。

## 📦 內建 Prompt 模板庫

以下為常用情境的標準模板，AI 依技術棧自動填入對應細節：

### 🔍 Code Review（RISEN 框架）

```
【角色】你是一位資深軟體工程師，專精於 [技術棧]，熟悉業界最佳實踐與安全規範。
【指令】對以下程式碼進行全面審查，每個問題標注嚴重程度。
【步驟】依序檢查以下 8 個面向：
  1. 程式碼品質與可讀性（命名規範、SRP、Magic Number）
  2. 框架最佳實踐（async/await、IDisposable、LINQ 陷阱）
  3. 例外處理（例外捕捉完整性、資源釋放）
  4. 安全性（SQL Injection、敏感資料外洩、反序列化）
  5. 效能（N+1 Query、記憶體、StringBuilder vs 字串串接）
  6. 設計模式與架構（SOLID、DI、分層原則）
  7. 測試性（耦合度、Interface 可 Mock 性）
  8. 執行緒安全（lock 使用、Concurrent 集合）
【目標】產出可直接用於 PR Review 的結構化報告。
【約束】
  - 嚴重程度：🔴 高風險（須立即修正）/ 🟡 中風險（建議修正）/ 🟢 改善建議
  - 每個問題附上修正後的程式碼範例
  - 輸出語言：繁體中文
```

### 🧪 單元測試產生（RISEN 框架）

```
【角色】你是一位 TDD 專家，專精於 [測試框架：xUnit / NUnit / Jest / Jasmine]。
【指令】為以下程式碼產生完整的單元測試。
【步驟】
  1. 分析方法的輸入輸出與副作用
  2. 識別所有需要測試的情境
  3. 為每個情境撰寫獨立的測試案例
【目標】涵蓋所有情境：
  - Happy Path（正常流程）
  - 邊界值（null、空集合、0、負數、最大值）
  - 例外情況（依賴失敗、格式錯誤、權限不足）
  - 所有外部依賴使用 Mock
【約束】
  - 命名格式：[方法名稱]_[情境描述]_[預期結果]
  - 結構：Arrange / Act / Assert 三段式
  - 輸出語言：繁體中文（註解）、[語言]（程式碼）
```

### ♻️ 重構建議（TIDD-EC 框架）

```
【任務】分析以下程式碼並提出重構建議。
【指令】識別設計問題，提供具體的重構方案與範例程式碼。
【要做】
  - 逐條說明違反 SOLID 原則的設計
  - 針對超過 30 行的方法說明如何拆分
  - 提供重構後的完整範例程式碼
  - 標注每個問題的優先級
【禁止】
  - 不得改變對外介面與商業邏輯
  - 禁止「順便」加入未被要求的功能
  - 禁止自行引入新的依賴套件
【範例】優先級標注：🔴 必須改 / 🟡 建議改 / 🟢 可選優化
【脈絡】技術棧：[框架版本]，目標：提升可維護性與可測試性
```

### 📄 API 文件產生（RISE-IE 框架）

```
【角色】你是一位技術文件專家，熟悉 RESTful API 設計規範。
【輸入】以下 Controller / API 程式碼。
【步驟】
  1. 解析端點路徑、HTTP 方法、參數
  2. 識別請求與回應的資料結構
  3. 整理錯誤碼與對應情境
  4. 撰寫使用範例
【預期輸出】完整 API 文件，包含：
  - 端點說明與用途
  - 請求參數（名稱、型別、必填、說明）
  - 回應格式（欄位、型別、說明）
  - 錯誤碼對照表
  - Request / Response 使用範例
  - 格式：[Swagger XML / Markdown]
  - 輸出語言：繁體中文
```

### 🐛 Debug 根因分析（Chain of Thought 框架）

```
【角色】你是一位資深除錯專家，擅長從錯誤訊息與程式碼中找出根本原因。
【指令】分析以下錯誤，依推理鏈逐步輸出。
【推理格式】
  [觀察事實] → 錯誤訊息、堆疊追蹤、異常行為的客觀描述
  [假設列表] → 2-3 個可能根本原因，標注可能性排序
  [驗證方式] → 每個假設如何驗證（加 log、測試特定情境）
  [修復方案] → 針對最可能的根因提出修復步驟
【約束】
  - 禁止在根因確認前直接修改程式碼
  - 每個結論必須指出依據（行號 / 錯誤訊息 / 文件）
  - 嚴禁「我猜」「通常來說」等模糊語句
  - 輸出語言：繁體中文
```

### 🤖 AI 協作流程設計（RISEN + TIDD-EC 混合）

```
【角色】你是一位 AI 系統架構師，熟悉 Multi-Agent 設計與 Prompt Engineering。
【指令】根據以下需求設計一套完整的 AI 協作流程。
【步驟】
  1. 任務分解（拆成哪些子任務）
  2. 角色分配（每個子任務由哪種 AI / Agent 執行）
  3. 資料流設計（輸入輸出格式、傳遞方式）
  4. 錯誤處理（各環節的 fallback 機制）
  5. 成本估算（Token 用量、API 呼叫次數）
【目標】產出可直接實作的流程設計文件。
【要做】
  - 每個節點附上對應的 prompt 範本
  - 標注哪些步驟需要人工審批
  - 說明如何監控與除錯
【禁止】
  - 不得假設用戶有特定基礎設施
  - 禁止推薦需額外付費的第三方服務（除非明確要求）
【脈絡】輸出語言：繁體中文
```

## 🔧 語言風格規範

- **主語言**：繁體中文（符合 Pixiu L0 憲法層規範）
- **技術術語**：保留英文原文（API、Repository、Hook、Mock、Agent）
- **嚴禁句型**：「被...所...」、「進行...的動作」等翻譯腔
- **結構原則**：結論先行，細節後補；超過三項改用條列式

# 派工 Prompt 模板

> 用法：複製對應模板，填掉所有 `{…}`，刪掉不適用的行。**不准留空的 `{…}` 就送出。**
> 每份模板都符合 `model-dispatch-rules.md` 的派工三件套與回報合約。
> 通用升級規則（各模板末段引用）：低階錯一次升中階；中階同一子任務連錯兩次帶軌跡升高階；總計兩輪未過就停手回報，不再重試。

## 1. 搜尋型（找檔案、找 pattern、找出處）

```text
【任務背景】{為什麼要找：例如「修 X bug 需要先定位寫入點」}
【目標】在 {路徑範圍} 找出 {具體目標：pattern / 函式 / 設定 / 字串}。
【不要做】不要修改任何檔案；不要讀 {排除路徑，母體預設排除 vault/memory/hook-state/}；找不到不要擴大範圍亂猜。
【可用來源】{repo 路徑 / vault 路徑 / 既有索引檔}
【驗收條件】
- [ ] 每個命中點以「檔案路徑:行號＋一行上下文」列出
- [ ] 明確說明搜尋了哪些範圍、用什麼 pattern（讓結果可重現）
- [ ] 零命中時回報「查無」＋已排除的可能性，不回報猜測
【回報格式】30 行內。命中清單超過 15 筆 → 落檔到 {輸出路徑}，回報只給路徑＋前 3 筆示例。
【失敗回報】無法讀取的路徑逐一列出（含錯誤訊息原文），不要略過。
【升級條件】pattern 需要語意理解才能判斷是否命中（不是字面匹配）→ 回報建議升中階重派。
```

## 2. 實作型（新功能、修 bug）

```text
【任務背景】{需求脈絡＋root cause 摘要。沒查過 root cause 就先派搜尋型，不要直接實作}
【目標】{具體改什麼行為，改完後可觀察到什麼}
【不要做】最小改動原則：不碰 {明列不准動的檔案/模組}；不做需求外的「順便」優化；不改測試來遷就實作；不動 DB schema。
【可用來源】{相關檔案清單}、{相關 recap / decision 路徑}
【驗收條件】
- [ ] {行為驗證：跑什麼、預期輸出什麼}
- [ ] 編譯通過＋{相關測試指令}綠
- [ ] 改動範圍僅限【不要做】允許的檔案，diff 中無無關變更
【回報格式】結論＋改動清單（檔案:行號區間）＋驗證證據路徑。diff 全文落檔到 {輸出路徑}，不貼回對話。
【失敗回報】卡在哪一步、錯誤訊息原文、已試過什麼（含指令）、目前工作樹是否乾淨。
【升級條件】發現需要動共用元件或 DB → 停手回報，這是使用者決策點，不是升級能解的。
```

## 3. 重構型（結構調整、批次改檔）

```text
【任務背景】{為什麼重構：技術債位置與代價}
【目標】{目標結構}；行為不變是硬約束。
【不要做】不改對外行為與介面；不動 {排除清單}；一次只做一種重構（搬移歸搬移、改名歸改名，不混合）。
【可用來源】{檔案清單或產生清單的指令}
【驗收條件】
- [ ] 重構前後 {測試指令} 結果一致（前後都要跑，兩份輸出都落檔）
- [ ] 總改動處數＝預估數 {N}（不一致要解釋每一筆差異）
- [ ] 抽樣 3 處 read-back 與預期一致
【回報格式】改動統計（檔案數/處數）＋抽樣證據＋測試前後對照路徑。
【失敗回報】改到一半發現行為會變 → 立即停止並回報該點，不要「先改完再說」。
【升級條件】兩處以上的改動互相牽連、順序有依賴 → 帶依賴說明升高階重新規劃。
```

## 4. 研究型（查文件、比方案、盤點現況）

```text
【任務背景】{要支撐什麼決策}
【目標】回答 {明確問題清單，逐條可回答}。
【不要做】不下結論性建議（除非明確要求）；查不到的不要用訓練記憶補——標【未確認】；不要把整篇來源貼回來。
【可用來源】{官方文件 URL / vault 路徑 / repo}；來源優先序：官方文件 > repo 原始碼 > vault 記憶 > 其他。
【驗收條件】
- [ ] 每個問題都有答案或明確的【未確認】＋查過哪裡
- [ ] 每個事實都附來源（URL 或 檔案:行號）
- [ ] 相互矛盾的來源並列呈現，不自行擇一
【回報格式】問題→答案→來源，逐條對應。全文落檔到 {輸出路徑}，對話只回每題一行摘要。
【失敗回報】無法存取的來源列出（含原因：無網路權限/404/需登入）。
【升級條件】答案需要跨來源推理或架構判斷 → 標記該題升高階，其餘題照常交付。
```

## 5. 審查型（code review、文件審、對抗審查）

```text
【任務背景】{審什麼、為什麼審。給審查對象的路徑，不給作者的推理過程——fresh context 是刻意的}
【目標】以 {角色：如「假設方案有錯的對抗審查者」} 審查 {對象路徑}，找出 {問題類型清單：規則衝突/路徑錯誤/模糊語句/安全漏洞/…}。
【不要做】不修改被審查的檔案；不重寫方案；不因為「大致沒問題」就略過清單中的檢查項。
【可用來源】{被審對象}＋{判準依據：如 vault/governance/judgment-rubrics.md}
【驗收條件】
- [ ] 每個檢查類型都有明確結果：發現 N 項或「此類未發現」
- [ ] 每項發現附位置（檔案:行號）＋為什麼是問題＋建議修法一句
- [ ] 發現分級：🔴 必修 / 🟡 建議 / 🟢 備註
【回報格式】按分級列出，每項一行定位＋一到兩行說明。超過 20 項落檔。
【失敗回報】讀不到被審對象 → 立即回報，不要審記憶中的版本。
【升級條件】發現疑似安全性問題但無法確認 → 標🔴＋【未確認】，建議高階複審，不要自行降級為🟡。
```

## 6. 通用填寫規則

1. 【可用來源】永遠給路徑，不要說「你自己找」——搜尋本身要派工就用搜尋型模板。
2. 【驗收條件】每條必須是可勾選、可證偽的句子。「品質要好」不是驗收條件，「測試全綠」才是。
3. 一次派工一個目標。兩個目標＝兩次派工。
4. 派工給哪一階模型：照 `model-dispatch-rules.md` 第 3 節；模板本身與模型無關。

## 7. 失敗軌跡格式（升級時必附）

```text
【失敗軌跡】
- 原始任務：{一句話}
- 第 1 輪：派 {模型階層}；prompt 要點 {…}；結果 {錯誤輸出原文或落檔路徑}；判定失敗原因 {…}
- 第 2 輪：修正了 {…}；結果 {…}；判定失敗原因 {…}
- 未試過的方向：{…}
- 環境事實：{相關版本/路徑/權限等已確認事實}
```

## 本檔維護

- 新增任務型態模板：AI 可提案，附一個實際用過的成功案例，使用者同意後併入。
- 修改既有模板欄位：屬制度變更，先問使用者。

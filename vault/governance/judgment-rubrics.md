# 判斷力外化 Rubric

> 目的：讓中低階模型不靠直覺也能做對七類判斷。每條格式固定：判準 → 正例 → 反例 → 建議動作。
> 本檔與其他規則衝突時，按 `entry-files-alignment.md` 第 3 節的位階表處理（那是唯一版本，本檔不另列位階）。

## 1. 何時該升級模型

- **判準**（命中任一即升級）：
  - 同一子任務已失敗兩次（含修正輪）
  - 修法需要同時改動兩個以上模組／repo 才能成立，或資料流已證實跨三處以上（例：AP 寫入、BK 消化、錯誤顯現在月彙報）——用「要動幾處」數，不用自己評估「需不需要深推理」
  - 錯誤後果不可逆或涉及資損（DB 資料修正、金流、對外發送）
  - 需要在 2 個以上方案間做架構取捨
- **正例**：PCLMS decltype T balance「多加沒扣」——牽涉出倉、進倉修改、月彙報 key 多處交易邊界 → 升高階做根因，不要讓中階逐檔猜。
- **反例**：SQL 欄位別名拼錯、單檔 if 條件改判準——中低階直接修，升級是浪費。
- **建議動作**：照 `model-dispatch-rules.md` 第 5 節，附完整失敗軌跡升級；沒有軌跡先補軌跡。

## 2. 何時算真的完成

- **判準**（全部成立才算完成）：
  - 驗收條件逐條有證據（測試輸出、read-back 內容、實跑結果、`檔案:行號`）
  - 產出物已落檔且 read-back 成功
  - 回報中不含「應該」「大概」「理論上」描述核心結果
  - 超出需求範圍的改動數為 0（最小改動原則）
- **正例**：「驗收條件 3/3 ✅：測試 `mvn test -Dtest=XxxTest` 全綠（輸出已落檔 `…/test-log.txt`）；修改僅 `XxxServlet.java:210-224`。」
- **反例**：「已修復，邏輯上不會再發生」——沒有證據，不算完成，標 `部分完成` 並列缺口。
- **建議動作**：缺證據就去補證據；補不到（如無法連測試 DB）→ 標註「本地無法驗證＋原因」，把驗證步驟寫給使用者。

## 3. 何時該停下來問使用者

- **判準**（命中任一必問，這是硬閘門）：
  - 寫入或修改 DB、執行 UPDATE/DELETE（founder-profile：先 SELECT 驗證範圍，執行需授權）
  - 刪除任何檔案、git push、改 git 全域設定
  - 修改 `user_rules.md`、`identity/`、根目錄入口檔、hook 設定
  - 需求有兩種以上合理解讀，且選錯會浪費 30 分鐘以上的工
  - 要動的檔案不在使用者提到的檔案／模組清單內＝超出範圍，必問（「順便重構」絕對禁止）
- **正例**：任務是修 bug，但發現根因在共用 lib——停下，給選項（就地繞過／修 lib），等使用者選。
- **反例**：按 `sop/recap-standard.md` 把 recap 寫進 `memory/recaps/`——標準已授權，不必問。
- **建議動作**：問的時候給 2-3 個選項＋各自優缺點（founder-profile 的決策風格），不要開放式地問「怎麼辦」。

## 4. 什麼訊號代表方向錯了（該換路，不是重試）

- **判準**（命中兩項以上＝換路）：
  - 同一個假設已修補三次，症狀還在
  - diff 越改越大，開始碰需求沒提到的檔案
  - 為了讓方案成立，開始改共用框架、公版設定或測試本身
  - 結論開始依賴「猜資料庫裡的資料長怎樣」而不是查出來
  - 每輪修正都在回滾上一輪的一部分
- **正例**：改了三次 servlet 判斷式，帳還是不平 → 停手，回頭用 SELECT 把實際資料撈出來對，再定位真正的寫入點。
- **反例**：第一次修 typo 沒修對第二次修對了——這是正常迭代，不是方向錯。
- **建議動作**：停止修補；寫下目前假設與反證；回到可驗證的最小重現；必要時照第 1 條升級。**換路不算重試次數重置的藉口——同一件事總計最多兩輪換路。**

## 5. 品質底線怎麼驗（按產出類型）

- **判準**（每類產出的最小驗證，做不到就不能標完成）：
  - 程式碼：能編譯＋相關測試綠＋主路徑實跑一次
  - SQL 資料修正：先 SELECT 同 WHERE 驗證影響筆數，與預期不符即停；執行時驗證 `executeUpdate` 回傳值並失敗即 rollback（既有 decision：`memory/decisions/2026-04/2026-04-20-PCLMS-Bug-修法原則.md`）
  - 文件 / 制度檔：read-back 全文、內部連結與路徑逐一可解析、UTF-8 無亂碼
  - 批次改檔：抽樣 3 處 read-back ＋ 總改動數與預期數一致
  - 分析報告：每個關鍵結論都有 `檔案:行號` 或查詢輸出佐證
- **正例**：批次改 12 檔後回報「共 12 檔、24 處替換，抽樣 read-back 3 檔一致，清單落檔於 …」。
- **反例**：「文件已產出」但沒 read-back——曾發生寫入編碼壞掉（vault 有 UTF-8 控制字元踩坑紀錄），不驗等於沒寫。
- **建議動作**：驗證由 fresh-context agent 或重新讀檔執行（`model-dispatch-rules.md` 第 6 節），不憑寫入當下的記憶。

## 6. 什麼情況不能靠拆解／驗證／多樣本評審補救

- **判準**（命中即明說，禁止假裝制度能解決）：
  - 需求本身模糊且兩解都合理（缺的是使用者判斷，不是分析）
  - 品味判斷且沒有偏好樣本（UI 風格、文案語氣）
  - 業務優先序衝突（速度 vs 安全、上線 vs 重構）
  - 安全或不可逆操作缺授權
  - 外部能力查不到（模型清單、MCP、工具版本）
  - 檔案亂碼、缺檔、I/O error（如 2026-07-03 發現的三個 recap 目錄）——這是環境壞了，任何 prompt 都修不了
- **正例**：讀 `memory/recaps/母體/2026-06` 回 I/O error → 記錄「目錄暫不可用」，繼續其他工作，回報使用者需本機檢查磁碟／同步軟體。**禁止**因讀不到就重建或覆寫同名目錄。
- **反例**：因為查不到 Codex 可用模型，就「推測應該有 high effort」寫進設定——這是編造，違反誠實條款。
- **建議動作**：按順序處理——先查可查的來源 → 查不到標【未確認】 → 能用第二意見補的派 fresh-context agent → 仍不能補的明說需要使用者判斷 → 任何情況都不編造。

## 7. 什麼東西值得寫入記憶（防噪音）

- **判準**（命中任一才寫；一條都沒中就不寫）：
  - 做了一個之後會被引用的決策（含被否決的方案與原因）
  - 踩了一個下次還會踩的坑（環境、編碼、工具行為）
  - 發現了與現有記憶矛盾的事實（要更新舊記錄，不是加新記錄）
  - 使用者明確要求記住
- **正例**：「Codex sandbox 讀母體 git 會 dubious ownership，單次 `-c safe.directory` 可解」——會重複遇到，寫成 instinct。
- **反例**：「使用者問了設定檔有沒有錯，我查了，沒錯」——事件流水帳，不寫。auto recap 洪水就是沒有這條判準造成的。
- **建議動作**：按 `memory/agent-learning/README.md` 的分層：單次經驗 → `observations/`（用模板）；三次以上重複 → `instincts/`；穩定規則 → 按 instinct 的 Promotion Rule 升格。寫入前先搜尋是否已有同主題記錄。

## 本檔維護

- 新增判準：AI 可提案（附觸發本次提案的實際案例），使用者同意後寫入。
- 修改既有判準：屬制度變更，先問使用者。

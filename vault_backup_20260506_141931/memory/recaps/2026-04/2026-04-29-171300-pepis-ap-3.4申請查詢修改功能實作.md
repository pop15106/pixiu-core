pepis_ap 是一個 eACH/eDDA 授權申請系統（Java JAX-RS 後端 + Vue.js Vuetify 前端）。

本次依規格 3.4 實作「申請查詢畫面的修改功能」：對狀態為**審查駁回(2)、授權駁回(5)、授權通過(4)**的案件，允許從查詢畫面按下修改按鈕，依當前申請類別動態顯示對應動作按鈕（授權 / 修改授權 / 終止授權），並依選擇限制可編輯欄位。

## 📐 核心邏輯

```
canModify = applyStatus in {2, 4, 5}

availableApplyTypes:
  applyType=1(授權)   + status 2/5 → [1]
  applyType=1(授權)   + status 4   → [2, 0]
  applyType=2/0       + any status → [2, 0]

選擇動作後欄位開放：
  1(授權)    → 說明2欄位可編輯，payLimit 強制 0
  2(修改授權) → 僅 payLimit 可編輯
  0(終止授權) → 全唯讀

送出：APPLY_TYPE = 新選類別，APPLY_STATUS = 0（立案/補件）
```

## 🎯 重要決策

| 決策點 | 選擇 | 原因 |
|--------|------|------|
| 3.4 流程識別方式 | 新增 `queryModify: boolean` 旗標 | status 2/5 在一般編輯流程也會出現，旗標可明確區分 3.4 來源 |
| 後端分支位置 | 在 `authDoc614DocUpdate` 加 `isQueryModify` 分支 | 避免新增 endpoint，復用現有更新邏輯 |
| 前端 dialogMode | 新增 `queryModify` mode | 與既有 edit/review/authorize/view 模式隔離，不污染現有按鈕邏輯 |
| 3.4.3 狀態歸位 | 納入本次實作（APPLY_STATUS = "0"） | 使用者確認一起做 |

## ⚠️ 踩坑與注意

- `queryEDDAAuthDoc` 的 SELECT 原本缺 `APPLY_TYPE`，`convertToAuthDocView` 讀的是欄位別名，需確認每個 query 的 SELECT 都有帶齊所需欄位

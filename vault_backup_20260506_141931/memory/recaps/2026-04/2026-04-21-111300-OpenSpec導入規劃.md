# Session Recap：OpenSpec 導入規劃

## 🎯 任務目標與背景

**目標**：將 OpenSpec（規格驅動開發框架）整合進 Pixiu 工作流程，讓每次功能開發前都有正式規格文件，解決 AI 需求偏移、紀錄分散在對話歷史的問題。

**背景**：使用者看到 [Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) 後認為這個工具的理念（先寫規格再寫程式）和 Pixiu 的開發哲學相符，希望導入艦隊。

**影響範圍**：
- 母體（PixiuCore）：新增 openspec/ 目錄作為中央管理層
- 子艦隊專案（PCLMS_AP、PCLMS_BK_new、PCLMS_FD 等）：透過註冊機制取得 config，各自持有 openspec/changes/ 規格資料夾

---

## ✅ 本次完成

1. **調查 OpenSpec repo** → 確認核心功能：`/opsx:propose`、`/opsx:apply`、`/opsx:archive` 三指令；每次功能開發產生獨立的 `openspec/changes/<name>/` 資料夾，含 proposal.md、specs/、design.md、tasks.md

4. **規劃 3 個實作 Phase** → 已定義每個 Phase 的工作項目與預估時間

## 📐 當前規劃完整內容

### OpenSpec 運作機制（重要背景）

```
開發者輸入：/opsx:propose add-dark-mode

→ 自動產生：
  openspec/changes/add-dark-mode/
  ├── proposal.md   ← 為什麼做、改什麼、影響範圍
  ├── specs/        ← 需求與驗收情境
  ├── design.md     ← 技術設計方案
  └── tasks.md      ← 實施 checklist（每項有驗證方式）

→ 實作：/opsx:apply（逐步執行 tasks.md）
→ 完成：/opsx:archive
  → 移至 openspec/changes/archive/2026-04-21-add-dark-mode/
```

### 中央化架構設計

```
PixiuCore/（母體）
├── openspec/
│   ├── templates/           ← 各類型專案的 config 範本
│   │   ├── java-web.yaml    ← PCLMS_AP 類型
│   │   ├── spring-boot.yaml ← PCLMS_BK_new 類型
│   │   ├── frontend.yaml    ← PCLMS_FD 類型
│   │   └── default.yaml     ← 通用備援
│   ├── registry.yaml        ← 已註冊的子專案清單
│   └── schemas/             ← 共用 schema 定義
└── scripts/
    └── openspec-register    ← 子專案執行這個腳本完成註冊

子專案（執行 register 後）：
PCLMS_AP/
└── openspec/
    ├── config.yaml          ← 從母體 templates/java-web.yaml 生成，輕量
    └── changes/             ← 規格資料夾，留在各自 repo（正確）
        └── <功能名稱>/
            ├── proposal.md
            ├── specs/
            ├── design.md
            └── tasks.md
```

### registry.yaml 格式設計

```yaml
registered:
  - id: PCLMS_AP
    path: <workspace-root>/PCLMS_AP
    template: java-web
    registered: 2026-04-21

  - id: PCLMS_BK_new
    path: <workspace-root>/PCLMS_BK_new
    template: spring-boot
    registered: 2026-04-21

  - id: PCLMS_FD
    path: <workspace-root>/PCLMS_FD
    template: frontend
    registered: 2026-04-21
```

### openspec-register 腳本行為（3 件事）

```bash
# 在子專案目錄執行：
/c/PixiuCore/scripts/openspec-register --type java-web

# 腳本做的事：
# 1. 讀 registry.yaml，確認該路徑尚未註冊（避免重複）
# 2. 從 templates/<type>.yaml 複製生成 ./openspec/config.yaml
# 3. 把專案資訊追加寫入母體的 registry.yaml
```

### config.yaml 內容方向（待設計細節）

```yaml
# 以 java-web.yaml 為例（內容待補）
schema: spec-driven
context: |
  這是 PCLMS 關務系統，Java Web 專案。
  語言：繁體中文（技術術語保留英文）。
  技術棧：Java / JSP / Servlet / Oracle DB。
  規範：遵循 Pixiu 治理規範，所有變更需用戶審批。
rules:
  proposal:
    - 描述清楚影響的 Servlet / Service / DAO 範圍
    - 標注是否需要 DB schema 變更
  tasks:
    - 每個 task 附上驗證方式（含 SQL 或 Log 確認）
```

### Phase 詳細工作項目

**Phase 1 — 母體建設（預估 30 分鐘）**
1. `npm install -g @fission-ai/openspec@latest`（全域，只裝一次）
2. 建立 `%PIXIU_CORE%\openspec\templates\` 目錄
3. 設計並寫入 java-web.yaml、spring-boot.yaml、frontend.yaml、default.yaml（⚠️ 需先確認內容）
4. 建立 `%PIXIU_CORE%\openspec\registry.yaml`（空白初始結構）

**Phase 2 — 註冊腳本（預估 30 分鐘）**
1. 撰寫 `%PIXIU_CORE%\scripts\openspec-register` bash 腳本
2. 實作：讀 registry 檢查重複 → 複製 template → 更新 registry
3. 加入錯誤處理（template 不存在、路徑無效等）

**Phase 3 — 驗證（預估 15 分鐘）**
1. 在 PCLMS_AP 執行 `openspec-register --type java-web`
2. 確認 `openspec/config.yaml` 正確生成
3. 測試 `/opsx:propose grnt-balance-fix`，確認 changes/ 資料夾正確產生
4. 測試 `/opsx:apply` 和 `/opsx:archive`

## 🎯 重要決策（含棄選方案）

| 決策點 | 選擇 | 棄選方案 | 原因 |
|--------|------|---------|------|
| OpenSpec 裝在哪裡 | 母體中央化管理（templates + registry） | 各專案各自 `openspec init` | 分散維護成本高、config 難以統一更新 |
| 是否在母體跑 `openspec init` | 否，只放 templates 和 registry | 在母體完整初始化 OpenSpec | 母體是配置 repo，加 npm 依賴 + openspec/changes/ 會污染結構 |
| 規格資料夾（changes/）放哪 | 留在各子專案 repo | 統一放母體 | 規格屬於各 repo 的 context，和 code 同 repo 才有意義 |
| CLI 安裝方式 | npm -g 全域裝一次 | 各專案 devDependency | skills 從母體注入，不需要各專案重複安裝 |
| 是否替換現有 /plan 流程 | 否，兩者並存 | 全面替換 | Pixiu /plan 已成熟，OpenSpec 補充「正式規格文件持久化」這一層 |

## 💡 補充筆記

OpenSpec 官方建議使用高推理能力模型（Claude Opus 4.5）執行 `/opsx:propose`，規劃階段品質較好。實作（`/opsx:apply`）用 Sonnet 即可。

現有 Pixiu 工作流程對照：
- `/opsx:propose` ≈ Pixiu `/plan`（但多了持久化規格文件）
- `/opsx:apply` ≈ 直接實作
- `/opsx:archive` ≈ git commit（但多了規格歸檔）

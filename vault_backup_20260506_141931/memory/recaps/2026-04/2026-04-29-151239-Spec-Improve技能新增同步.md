## 📐 當前規劃完整內容

### 技能定位

`spec-improve` 是既有 spec 的翻修/審查技能，不取代 `spec`。它像老屋翻修前的結構鑑定：先看地基與樑柱是否穩，再決定補哪裡，而不是直接開始施工。

### 核心流程

1. 判斷目標來源：指定 spec folder、未指定時掃 `specs/active/`、或直接審查聊天中貼上的 raw spec。
2. 讀取必要輸入：優先 `spec.md`，視需要讀 `plan.md`、`tasks.md`、`docs/DESIGN.md` 或鄰近 completed specs。
3. 依 100 分 rubric 評分：
   - Goal clarity 15
   - Scope and boundaries 15
   - Acceptance criteria 20
   - Inputs and outputs 10
   - Edge cases and failure paths 10
   - Technical feasibility 10
   - Test strategy 10
   - Task readiness 10
4. 輸出評分、優點、缺點/風險、建議補強與最多 5 個澄清問題。
5. User 回答後，只重新評估受影響構面，接著提供三種下一步：Patch proposal only、Rewrite draft、Apply changes。
6. 未經 user 明確確認，不修改任何 spec 檔案。

### YAML metadata 慣例

YAML 只放在：

```text
.agents/skills/spec-improve/agents/openai.yaml
```

`skills/spec-improve` 與 `.agent/skills/spec-improve` 只放 `SKILL.md`。

### 驗證方式

- 六份 `SKILL.md` 使用 SHA256 hash 比對，結果一致。
- `Select-String TODO` 無結果。
- `.agents` 兩邊的 `openai.yaml` 已人工讀取確認內容一致。

## 🎯 重要決策（含棄選方案）

| 決策點 | 選擇 | 棄選方案 | 原因 |
|--------|------|---------|------|
| 技能型態 | 新增獨立 `spec-improve` | 直接修改原 `spec` 技能 | 避免污染原本建立新 spec 的流程，讓既有規格審查與翻修獨立。 |
| 範圍邊界 | 只針對 `spec` | 納入 `make-docx` | `make-docx` 只是文件輸出工具，不應混入規格品質審查流程。 |
| YAML 位置 | 僅 `.agents\skills\spec-improve\agents\openai.yaml` | 三處都放 YAML | 盤點現況後確認 YAML metadata 慣例在 `.agents\skills`，避免其他技能掃描器誤讀。 |
| 同步策略 | 母體與 gravityTest 同步建立同名資料夾 | 只改母體 | gravityTest 是版本基底，需要同步保留可追蹤版本。 |

## ⚠️ 發現的問題 / 踩坑

- `python` 不在 PATH，後續執行技能建立工具時需使用 Codex bundled Python：`%USERPROFILE%\.cache\codex-runtimes\codex-primary-runtime\dependencies\python\python.exe`。
- `quick_validate.py` 需要 `yaml` 模組，但 bundled Python 目前沒有，導致官方驗證工具不能完成。
- `%PIXIU_CORE%` 雖有 `.git` 目錄，但 `git rev-parse` 回報不是有效 repo；目前可追蹤版本以 `<workspace-root>\pixiu-core` 為主。
- gravityTest repo 存在既有未追蹤與修改項目，不應在本次任務中混合處理或 revert。
